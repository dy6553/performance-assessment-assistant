새 기능은 기존 Local-first 구조 위에 추가하세요.

## 1. 목표 동작

### 기기 1대 사용자

사용자가 따로 설정하지 않아도:

1. 작업 내용을 기기에 즉시 저장
2. 변경 내용을 자동 감지
3. 기기에서 암호화
4. Supabase에 암호화된 형태로 자동 백업
5. 인터넷이 끊기면 로컬 큐에 보관
6. 인터넷 복구 시 자동 재전송

### 기기 2대 이상 사용자

같은 계정으로 두 번째 기기에서 로그인하면 자동으로 새 기기를 등록하고 기존 암호화 데이터를 확인해 필요한 변경분만 다운로드하고, 기기에서 복호화하여 IndexedDB/OPFS에 반영하세요. 이후 양쪽 기기의 변경 사항을 자동 동기화하세요. 사용자가 “1대/2대”를 직접 선택하지 않게 하세요.

## 2. 기기 식별

각 설치/브라우저 프로필별로 안정적인 `device_id`를 생성하세요.

예시 테이블 `user_devices`:

- `id`
- `user_id`
- `device_id`
- `device_name`
- `platform`
- `created_at`
- `last_seen_at`
- `last_sync_at`
- `revoked_at`

요구사항:

- 같은 계정이라도 기기마다 서로 다른 ID
- 앱 실행/복귀 시 last_seen 갱신
- 현재 기기 표시
- 다른 기기 연결 해제 지원
- revoked 기기는 이후 동기화 불가
- 다른 사용자의 기기/데이터 접근 불가
- RLS 정책 적용

## 3. 서버 동기화 레코드

예시 테이블 `encrypted_sync_records`:

- `user_id`
- `record_id`
- `record_type`
- `version`
- `source_device_id`
- `updated_at`
- `deleted_at`
- `encrypted_payload`
- `payload_iv`
- `payload_schema_version`
- `content_hash`

서버 DB에는 학습 내용, 수행평가 본문, AI 채팅 원문 등의 평문을 최대한 저장하지 마세요. 서버는 암호문과 동기화 메타데이터 중심으로 동작하게 하고 RLS로 `auth.uid() = user_id` 범위를 강제하세요.

## 4. 암호화

클라이언트 측 암호화를 구현하세요.

- AES-256-GCM
- 레코드/파일마다 고유 IV
- Web Crypto API
- 변조/무결성 실패 시 복호화 거부
- 민감 원문은 업로드 전 암호화
- 다운로드 후 클라이언트에서 복호화
- 원본 복호화 키를 일반 Supabase DB 컬럼, 로그, 분석 이벤트에 저장 금지

자동 동기화이므로 사용자가 매번 비밀번호를 입력하게 하지 마세요. 계정별 동기화 키 또는 이에 준하는 안전한 키 관리 구조를 설계/구현하고 새 기기 로그인 시 계정 인증 후 키를 안전하게 복구/전달할 수 있어야 합니다. 보안상 더 적절한 구조가 있다면 개선하되 이유를 문서에 남기세요.

## 5. Local-first 원칙

모든 작성/수정은 순서상:

1. IndexedDB/OPFS 로컬 저장
2. sync queue 등록
3. 백그라운드 동기화

로 처리하세요. 서버 장애/오프라인 상태에서도 작성, 수정, 열람이 가능해야 합니다.

## 6. 자동 동기화 트리거

최소한 다음 시점에 동기화를 시도하세요.

- 로컬 데이터 변경 후 debounce
- 앱 시작
- 로그인 완료
- `visibilitychange`로 앱 복귀
- `online` 이벤트
- 주요 저장 완료
- 사용자가 누르는 “지금 동기화”

과도한 API 호출을 피하도록 debounce/batching을 적용하세요. 권장 debounce는 약 1~2초이며 현재 구조에 맞게 조절할 수 있습니다.

## 7. 재시도 큐

동기화 실패가 데이터 유실로 이어지지 않도록 persistent sync queue를 만드세요.

- 실패 항목 유지
- 네트워크 복구 시 재시도
- 중복 요청 방지
- exponential backoff 또는 이에 준하는 재시도 제어
- 같은 record/version의 중복 업로드 방지
- 성공 후 큐 제거
- 새로고침/앱 재실행 후 미전송 항목 복구

## 8. 버전 및 충돌 처리

단순 `updated_at` 최신값으로 무조건 덮어쓰지 마세요.

- 서로 다른 record 수정 → 자동 병합
- 한쪽에서만 수정 → 최신 version 적용
- 동일 record를 서로 다른 기기에서 동시에 수정 → 충돌 감지

중요 문서의 충돌이 감지되면 양쪽 버전을 보존하고 `휴대폰 버전 사용 / 태블릿 버전 사용 / 둘 다 보관` 선택 UI를 제공하세요. 초안/완성본/중요 결과물은 silent overwrite 금지입니다.

## 9. 삭제 동기화

삭제 즉시 hard delete하지 마세요. `tombstone` 방식으로 `deleted_at`을 설정하고 다른 기기로 삭제 상태를 동기화한 뒤 기존 7일 휴지통 정책과 결합해 유예기간 이후 완전 삭제하세요. 오래 오프라인이었던 기기가 삭제된 데이터를 다시 살려내지 못하도록 version/tombstone 비교를 정확히 구현하세요.

최소한 다음을 연결하세요.

- 캘린더
- 첨부파일 메타데이터

대용량 파일은 DB에 base64로 넣지 말고 기기에서 암호화한 후 Supabase Storage에 업로드하세요. 변경되지 않은 파일을 매번 다시 올리지 않도록 content hash/version 기반으로 처리하세요.

## 14. 기존 수동 암호화 백업 유지

현재 수동 암호화 파일 백업 기능은 삭제하지 마세요.

- 시험온: `.examon-backup`
- 수행도우미: `.assessment-backup`

자동 동기화 기능 추가 후에도 기존 백업 파일 생성/복원이 정상 작동하는지 회귀 테스트하세요.

## 15. Supabase 구현

각 프로젝트의 Supabase에 필요한 migration을 실제로 적용하세요.

- 동기화 관련 테이블
- 인덱스
- RLS
- 필요한 Storage bucket 및 정책
- 오래된 tombstone/암호화 파일 정리 전략
- 사용자별 접근 제어
- 필요한 RPC가 있다면 최소 권한으로 추가

Service Role Key를 클라이언트에 노출하지 마세요. 클라이언트에는 공개 가능한 Supabase 설정만 사용하고 모든 권한은 RLS/정책으로 보호하세요.

- 다른 계정 Storage 접근 실패
