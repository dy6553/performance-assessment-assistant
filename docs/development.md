# 수행도우미 개발 절차

## 로컬 개발

일반적인 Next.js 개발 흐름을 따른다.

- 의존성 설치
- 개발 서버 실행
- 타입/린트 오류 확인
- 변경 기능 수동 확인

환경변수는 저장소에 실제 비밀값을 커밋하지 않고 `.env.example`을 기준으로 관리한다.

## 기능 수정 순서

1. 현재 관련 파일을 먼저 읽는다.
2. 기존 상태 저장, 라우팅, API 계약을 확인한다.
3. 사용자 요청 범위만 수정한다.
4. 구조화 AI 응답이면 스키마와 출력 계약을 함께 점검한다.
5. 모바일 UI에서 긴 스크롤과 버튼 접근성을 확인한다.
6. GitHub `main`에 반영한다.
7. Vercel production 배포 상태를 확인한다.
8. 배포가 `READY`가 된 뒤 완료로 보고한다.

## UI 변경 체크리스트

- 모바일 화면에서 좌우 넘침이 없는가
- 불필요한 상하 여백이 과도하지 않은가
- 결과가 한 페이지에 과도하게 누적되지 않는가
- 주요 버튼이 긴 스크롤 끝에만 있지 않은가
- 다크모드/라이트모드에서 읽기 가능한가
- 로딩/오류/성공 상태가 명확한가

## AI 기능 변경 체크리스트

- 과목/학년/형식 문맥이 라우터에 전달되는가
- 난이도 1~7이 필요한 기능에서 반영되는가
- 승인된 모델만 사용되는가
- fallback 모델도 승인 후보인가
- 출력 JSON 키와 자료형이 스키마와 일치하는가
- 불확실한 최신 사실을 확정하지 않는가
- 오류 메시지가 사용자 친화적인가

## 배포 확인

Vercel 배포에서 확인할 항목:

- target이 production인지
- 최신 GitHub commit SHA와 일치하는지
- build error가 없는지
- deployment state가 `READY`인지
- 기능 오류를 수정한 경우 관련 runtime log에 같은 오류가 반복되지 않는지

빌드가 `BUILDING`인 동안에는 배포 완료라고 표현하지 않는다.

## 큰 파일 수정

`assessment-wizard.tsx`처럼 큰 파일은 전체 교체 시 충돌 위험이 있다.

- 변경 직전 최신 파일 SHA를 다시 확인한다.
- 가능하면 기능을 별도 컴포넌트/페이지로 분리한다.
- 동일 파일을 연속 수정할 경우 최신 content SHA를 사용한다.
